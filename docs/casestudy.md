## 背景・目的

- DOA6のコスチューム差分情報がインターネット上に見当たらず、自前のメモを用意して利用していた。せっかくなので公開することにした。
- このサイトでは複雑な機能は必要としないので、**「メンテナンス性の高い、シンプルな構築」「データの追加にかかる手間を必要最小限にする作り」「ランニングコストが限りなく低いこと」** をテーマにサイトを制作した。
- 同時に、AI プログラミングを実務的に使いこなす練習台として、設計判断を自分の言葉で説明できる状態を作ることを裏目的にした。

## 課題と解決（意思決定の物語）

このサイトで実際に直面した課題を、「問題 → 選択肢 → 比較 → 選んだ理由 → 結果」の流れで並べています。
どの判断も、思いつきではなく選択肢を比べたうえで根拠を持って選んでいます。

### 1. 大量の項目をどう開閉表示するか

- **問題**: コスチュームが多く、全部を常時展開すると縦に長すぎて閲覧しづらい。折りたたみが要る。
- **選択肢**:
  - A) JSライブラリでアコーディオンを実装する
  - B) 自前で JS を書いて開閉を制御する
  - C) HTML ネイティブの `<details>` / `<summary>` を使う
- **選んだもの**: C（ネイティブ `<details>`）。
- **理由**: 静的サイトで JS 依存を増やしたくなかった。ネイティブ要素なら追加コストゼロで、アクセシビリティ（キーボード操作・スクリーンリーダー）も標準で担保される。保守も楽。
- **結果**: 依存を増やさず開閉を実現。静的サイトの軽さを保てた。

### 2. 「閉じるのに上まで戻る問題」への気づきと対応

- **問題**: 開いた項目を閉じるとき、開閉トリガーが項目の先頭にあるため、長い項目だと閉じるのに画面上部までスクロールして戻る必要があり、体験が悪い。
- **気づき**: これは実際に触って初めて分かる類の問題。機能一覧には出てこない「使い勝手」の課題。
- **選択肢**:
  - A) 一律で末尾にも閉じるボタンを置く
  - B) デバイスによって最適な手段が違うと考え、出し分ける
- **選んだもの**: B（デバイス別に設計）。
  - PC: 見出しを `sticky` にして、スクロールしても閉じるトリガーが画面内に残るようにする
  - スマホ: 画面が狭く sticky が邪魔になりやすいので、項目末尾に閉じるボタンを置く
- **理由**: PC とスマホでは画面サイズと操作（マウス/タッチ）が違うので、同じ解決策が最適とは限らない。ユーザーの操作文脈に合わせた。
- **結果**: どちらのデバイスでも「戻らずに閉じられる」体験にできた。

### 3. 英語対応をどう実現するか（更新コストを軸にした比較）

- **問題**: 多言語対応したいが、日本語と英語で別々にページを管理すると更新のたびに二重作業になり、破綻する。
- **選択肢**:
  - 案A) 日本語ページと英語ページを別々に手で管理する
  - 案B) 翻訳サービスに丸投げする（機械翻訳の埋め込み等）
  - 案C) Astro i18n を使い、**データ（内容）とビュー（表示）を分離**して、1データに ja/en 両方を持たせる
- **選んだもの**: 案C。
- **理由**: 判断軸を「更新コスト（コンテンツ追加時の手間）」に置いた。案A は二重管理で破綻、案B は品質とニュアンス（このサイトのカジュアルな語り口）を制御できない。案C なら **1箇所のデータを直せば両言語に反映**でき、追加も一元化できる。
- **結果**: コスチューム追加は `src/data/costumes.ts` の 1 箇所を編集するだけで ja/en 両方に反映される保守性を獲得。

### 4. データとビューの分離（3で選んだ案Cの具体的な構造）

- **問題**: 内容（コスチュームの情報）と表示ロジックが混ざると、追加・修正のたびに壊しやすい。
- **選んだもの**: コンテンツを `src/data/costumes.ts` に集約し、表示は `src/components/CostumeGuide.astro` に分離。ページ（`/` と `/en/`）はコンポーネントを呼ぶだけにした。
- **理由**: 「追加運用が一番発生する部分（データ）」を、表示から切り離して安全に触れるようにするため。
- **結果**: 3 の i18n とも噛み合い、`{ ja, en }` 構造のデータを 1 箇所編集する運用に統一できた。

### 5. SEO と、訪問者ごとの言語振り分け

- **問題**: 多言語サイトは検索エンジンに正しく評価されにくい。かつ、日本語話者と英語話者で最適な入口が違う。
- **やったこと**:
  - `hreflang` / `canonical` / `site` 設定で、ja/en の対応関係を検索エンジンに正しく伝える
  - Cloudflare Pages Functions で、トップ（`/`）アクセス時に訪問者のブラウザ言語（`Accept-Language`）を見て英語話者を `/en/` へ振り分ける（エッジで実行）
- **ここで悩んで決めたこと（SEO を壊さない工夫）**:
  - **クローラーは振り分けない**: googlebot 等の UA は判定せず日本語版をそのまま返す（クローキング回避・インデックスの一貫性）
  - **301 ではなく 302 を使う**: 恒久的な統合と誤認されないように、あくまで一時的な振り分けとして扱う
  - **cookie(lang) で記憶**: 一度言語が決まったら再判定しない。毎回リダイレクトして体験を損なわないため
  - cookie 同意の要否まで検討した（機能上必須の言語記憶に限定）
- **理由**: 「便利な自動振り分け」と「SEO の健全性」はトレードオフになりやすい。両立させるため、対象を `/` のみに限定し、クローラー除外・302・記憶を組み合わせた。
- **結果**: 人間の訪問者には言語に応じた入口を、検索エンジンには一貫したインデックスを提供する形に落とし込んだ。

### 6. Git 事故からの復旧

- **問題**: Git の操作ミスで作業内容を失いかけた。
- **やったこと**: VS Code のローカル履歴（Local History）を使って、コミット外の変更を復元した。
- **学び**: バージョン管理の外側にも救済手段があること、そして日頃のコミット粒度の重要性を実感した。

## 技術的なハイライト（まとめ）

- **静的サイト（Astro `output: static`）** で配信し、ホスティングは Cloudflare Pages。サイト運営コストが0円。
- **データ駆動 + i18n**: `{ ja, en }` 構造のデータを 1 箇所に集約し、ビューと分離。フォールバック（en が空なら ja）も実装。
- **エッジでの言語振り分け**: Cloudflare Pages Functions（`Accept-Language` 判定）を、SEO を壊さない条件（クローラー除外・302・cookie 記憶）付きで実装。
- **依存を増やさない UI**: 開閉はネイティブ `<details>`。JS 追加なしでアクセシビリティも確保。
